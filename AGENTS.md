## 0. Разделение ролей

**Claude отвечает за логику.** Архитектура, контракты инструментов, правила
поведения агента, приёмочные критерии, приоритеты задач, тексты системного
промпта. Всё это зафиксировано в этом файле и меняется только через Claude.

**Codex отвечает за написание кода.** Реализация по спецификации ниже:
файлы, функции, компоненты, миграции, стили, тесты, отладка.

### Правила для Codex

1. Этот файл — источник истины. Если код расходится со спецификацией,
   прав файл, а не код.
2. Не менять самостоятельно: сигнатуры инструментов (раздел 5), правило
   подтверждения (раздел 6), приёмочные критерии (раздел 9), выбор стека
   (раздел 2).
3. Если требование неоднозначно или спецификация противоречит сама себе —
   **остановиться и спросить**, не додумывать. Неверная догадка стоит
   дороже вопроса: на весь проект пять часов.
4. Можно и нужно решать самостоятельно: имена переменных, внутреннюю
   структуру функций, выбор мелких утилит, вёрстку, обработку ошибок.
5. Работать по очереди задач из раздела 10, строго по приоритетам.
   Не начинать P1, пока не зелёные все P0.
6. Никаких новых зависимостей без необходимости. Каждая библиотека —
   риск, что сборка встанет в день хакатона.
7. Идентификаторы в коде — на английском. Пользовательские тексты
   интерфейса — на русском.

## 2. Стек

| Что | Решение |
|---|---|
| Фреймворк | Next.js (App Router) + TypeScript, один репозиторий |
| Агентный цикл | Route handler на сервере, tool-calling |
| База | SQLite через `@libsql/client`, засев при старте из seed-файла |
| Стили | Обычный CSS-модуль `globals.css`. **Tailwind не ставим** |
| Деплой | Vercel, `vercel --prod` |
| Запасной путь | туннель с ноутбука (`cloudflared` / `ngrok`) |

Состояние между сессиями не требуется: на serverless файловая база не
переживает перезапуск, и это нормально — каждый прогон демо начинается
с чистого каталога. Не тратить время на внешнюю БД.

Ключ к модели — только на сервере. В браузер не попадает никогда.

**Почему не Tailwind.** Пункт 6 раздела 0 запрещает лишние зависимости, а
трёхзонная вёрстка уже написана обычным CSS и работает. Установка Tailwind
и перенос стилей — это 40–60 минут, которые не добавляют жюри ни одного
балла. Правило раздела 0 важнее строчки в таблице.

**Логин и пароль к API партнёра, ключ модели — только в `.env.local`.**
В репозиторий не коммитятся никогда. В `.env.example` — пустые значения.

## 4. Данные

**Каталог берём из живого API партнёра, а не выдумываем.** ТЗ разрешает
синтетику, но не требует её, а у нас есть доступ к боевым данным ekt.kz:
настоящие характеристики, настоящие остатки по 24 складам и собственные
связи «рекомендуемых» товаров. Для жюри и для партнёра в зале это
несопоставимо сильнее рукописных тридцати позиций.

### Доступ

```
basicAuth: apiuser / <пароль из .env>
GET https://ekt.kz/api/products?page=N        -> { page, per_page: 20, count, items[] }
GET https://ekt.kz/api/products/detail?id=ID  -> карточка с характеристиками и складами
```

`count` — это размер страницы, а не общее число товаров. Каталог большой:
страница 200 всё ещё отдаёт данные. Выгружаем **срез**, а не всё.

### Как выгружаем

`scripts/seed-from-api.ts` ходит в API **один раз**, собирает срез и пишет
`data/catalog.json`, который коммитится в репозиторий. В рантайме сеть к
ekt.kz не нужна: приложение читает SQLite, засеянный из этого файла.
Демонстрация не должна зависеть от чужого API и от Wi-Fi площадки.

Параметры среза: 250–400 товаров. На каждый товар — один запрос detail
(список характеристик и остатков есть только там). Между запросами пауза
100–150 мс, не долбить партнёрский сервер. Прогресс в консоль.

Обязательно добиться, чтобы в срезе оказались:
- не меньше 5 позиций с нулевым суммарным остатком (для теста 2);
- не меньше 5 позиций с остатком 1–3 штуки (для ограничения количества);
- позиции с непустым `properties.RECOMMEND` (для `find_alternatives`).

Если срез вышел без них — добрать страницами, а не подрисовывать руками.

### Соответствие полей

| Наше поле | Источник в API |
|---|---|
| `sku` | `properties.ARTIKULPOSTAVSHCHIKA`, иначе `article` |
| `name` | `name`, очищенное от префикса `***` и ведущего артикула |
| `category` | предпоследний сегмент пути в `url` (`/catalog/<раздел>/<подраздел>/...`) |
| `categoryTitle` | `properties.OBYEM` — человекочитаемый тип («Автоматический выключатель») |
| `brand` | `properties.TORGOVAYA_MARKA` |
| `specs` | отобранные ключи `properties` (см. ниже) |
| `price` | `price` |
| `stock` | `stores[]`, **отфильтрованные** (см. раздел 12) |
| `status` | `in_stock` при сумме > 0, иначе `out_of_stock` |
| `alternatives` | `properties.RECOMMEND` — id рекомендуемых товаров партнёра |
| `minOrder` | `properties.KRATNOST_MIN`, по умолчанию 1 |
| `url` | `url` — ссылка на карточку на сайте |
| `certificate` | **в API отсутствует, синтезируем** (см. ниже) |

В `specs` кладём только осмысленные технические ключи, с человеческими
подписями: `NOMINALNYY_TOK` → «Номинальный ток», `KOLICHESTVO_POLYUSOV` →
«Количество полюсов», `NOMINALNOE_NAPRYAZHENIE` → «Номинальное напряжение»,
`NOMINALNAYA_OTKLYUCHAYUSHCHAYA_SPOSOBNOST` → «Отключающая способность»,
`TIP_USTANOVKI` → «Тип установки». Служебные ключи (`BRAND_PRIORITY`,
`CML2_TRAITS`, `CML2_TAXES`, `NOVINKA`, `IMYAKARTINKI`) в `specs` не попадают.

### Сертификаты

Единственное синтетическое поле. В API их нет, а приёмочный тест 1 их
требует. Проставляем `certificate` примерно трети позиций, детерминированно
по `sku`, и **помечаем в README и в интерфейсе как демонстрационные**.
Выдавать выдуманный сертификат за настоящий нельзя — это ровно тот
«недостоверный ответ», который запрещён разделом 11.

### Условия покупки

`terms.json` — оплата, доставка, минимальная партия, самовывоз. Здесь
синтетика уместна: этих данных в API нет. Опираться на то, что реально
написано на ekt.kz, если успеем посмотреть.

## 5. Инструменты агента

Все инструменты — тонкие обёртки над SQLite. Никакой логики модели внутри.

| Инструмент | Вход | Выход |
|---|---|---|
| `search_catalog` | `query`, опц. `category` | до 5 позиций: sku, name, price, status |
| `get_product` | `sku` | полная карточка: характеристики, сертификат, цена, остатки по складам |
| `find_alternatives` | `sku` | список аналогов с ненулевым остатком, **у каждого — поле `reason`** с кратким обоснованием подбора |
| `get_terms` | `topic`: payment \| delivery \| min_order \| all | текст условий |
| `propose_add` | `sku`, `qty` | `{ proposalId, sku, name, qty, price, available }` — предложение, корзина не меняется |
| `confirm_add` | `proposalId` | обновлённая корзина |
| `get_cart` | — | позиции, количества, сумма |
| `get_cart_link` | — | URL страницы корзины с актуальным состоянием |

Объяснимость рекомендаций вынесена в требования кейса отдельным пунктом,
поэтому `reason` в `find_alternatives` — обязательное поле, а не украшение.

## 6. Правило подтверждения — стержень решения

> Корзина изменяется **только** после явного подтверждения клиента.

Это не строчка в промпте, а инвариант в коде:

1. Агент никогда не вызывает `confirm_add` сам. Он вызывает `propose_add`
   и получает `proposalId`.
2. `propose_add` записывает предложение на сервере со статусом `pending`
   и сроком жизни в рамках сессии. Корзину не трогает.
3. `confirm_add` выполняется, только если получен `proposalId` в статусе
   `pending`, порождённый в этой же сессии. Иначе — отказ.
4. Подтверждение приходит **от пользователя**, двумя путями. В обоих
   решение принимает сервер, а не модель — иначе инвариант превращается
   в декорацию, и первый же вопрос жюри его сломает.

   **Путь А, кнопка.** `POST /api/confirm { proposalId }` идёт из интерфейса
   напрямую в сервер, минуя модель. Модель этот вызов подделать не может,
   потому что она в нём не участвует.

   **Путь Б, текст.** Модель вправе вызвать `confirm_add(proposalId)`, но
   сервер исполняет его, только если **последняя реплика пользователя**
   в этой сессии проходит проверку на согласие. Сырой текст реплики сервер
   сохраняет сам в начале обработки запроса — модель на него не влияет
   и подменить его не может.

   Матчер согласия — консервативный. Срабатывает на явных формах:
   «да», «да, добавь», «добавь», «давай», «подтверждаю», «беру», «ок»,
   «хорошо, добавь». Не срабатывает на вопросах («а можно добавить?»),
   на условных («если есть на складе, добавь») и при наличии отрицания
   («нет», «не надо», «отмени», «пока не»). Сомнительный случай трактуем
   как отказ: не добавить по ошибке дешевле, чем добавить без спроса.

   Отказ возвращается модели текстом, и она переспрашивает пользователя.
5. `qty` при подтверждении не может превысить суммарный остаток. Если
   превышает — добавляется доступное количество, и агент явно сообщает
   об этом.
6. Один `proposalId` срабатывает один раз, затем переходит в `used`.

Если модель попытается вызвать `confirm_add` без пользовательского
подтверждения — инструмент возвращает ошибку. Защита живёт на сервере,
а не в инструкциях модели. Это главный пункт, который нужно уметь
показать жюри.

## 7. Слой доступа к модели

Две точки входа, и других нет. `openai` больше нигде не импортируется.

| Файл | Функция | Для чего |
|---|---|---|
| `src/lib/llm/client.ts` | `completeStream()` | ходы агента, со стримингом и вызовами инструментов |
| `src/lib/llm/vision.ts` | `extractFromImage()` | одноразовое чтение фото, без стриминга, вне агентного цикла |

Картинка в поток сообщений модели не попадает: vision отдаёт короткий
JSON, дальше работает обычный поиск по каталогу. Так стриминг и ретраи
остаются в одном месте и не переписываются ради вложений.

- **Mock-режим** — переключатель по переменной окружения. При включении
  ответы берутся из `src/lib/llm/mock.ts` вместо сети. На площадке
  2500 участников и Wi-Fi ляжет; демо обязано пройти сценарий до конца
  без интернета. Записать моки сразу после того, как заработает
  основной сценарий, не откладывать.
- **Стриминг** обязателен. Без него жюри смотрит на спиннер.
- Таймаут на запрос, ретраи с экспоненциальной задержкой.
- Валидация структурированного ответа схемой, одна попытка починки.
- Запасная модель подешевле при rate limit.
- Лог вызовов и токенов в консоль сервера.
- Имя модели — одна константа. Доступы могут выдать прямо на площадке.

## 8. Интерфейс

Одна страница, три зоны, видимые **одновременно**:

- сетка карточек товара (артикул, наименование, цена, остаток);
- панель чата;
- **корзина, постоянно видимая на экране**.

Корзина на отдельной странице ломает весь смысл демонстрации: жюри должно
видеть, как строка появляется в корзине в момент действия агента, а не
читать сообщение «я добавил товар». При изменении — подсветка строки
на 1–2 секунды.

Карточка подтверждения в чате: наименование, количество, цена, кнопки
«Да» / «Нет».

Мобильная вёрстка в требованиях кейса: на узком экране сетка в одну
колонку, чат на весь экран снизу, корзина — сворачиваемая полоса сверху
со счётчиком.

## 9. Приёмочные тесты

Сформулированы в задании как проверки — вероятнее всего, жюри спросит
именно так. Это же сценарий демонстрации, в этом порядке.

1. Запрос по существующему артикулу → верные данные о наличии,
   технические характеристики, ссылка на сертификат, если он есть в базе.
2. Запрос по позиции с нулевым остатком → минимум один аналог
   с кратким обоснованием.
3. Вопрос об условиях покупки → содержательный ответ.
4. Просьба добавить товар **без** явного «да» → корзина не изменилась.
   Затем подтверждение → позиция добавлена, количество не превышает остаток.
5. Ссылка на корзину ведёт на актуальное состояние.

## 11. Запреты

Из требований кейса, нарушать нельзя:

- оформлять заказ; финальный шаг — только ссылка на корзину;
- запрашивать или хранить платёжные данные;
- изменять состав корзины без явного подтверждения;
- сообщать недостоверные данные о цене или наличии — все числа только
  из инструментов, модель их не придумывает и не пересчитывает.

Если данных по запросу нет — агент говорит, что не нашёл, и предлагает
уточнить или связаться с менеджером. Выдумывать артикулы запрещено.

## 12. Достоверность данных — следствия из боевого API

Раздел 11 запрещает недостоверные данные о цене и наличии. На реальной
выгрузке ekt.kz это не абстракция: там есть три конкретные ловушки.

### 12.1 Не все склады — торговые

В `stores[]` вперемешку лежат настоящие городские склады и служебные:
«Брак MEGALIGHT», «Востановленный продукт», «перемещение», «Образцы Отдел
Закупа», «Витрина ТЗ», «Маркетинг MEGALIGHT».

Остаток с них **не считается доступным**. «Брак» — это брак; показать его
как наличие значит соврать клиенту о наличии товара.

Фильтр по ключевым словам в названии склада, регистронезависимо:
`брак`, `востановлен`, `восстановлен`, `перемещен`, `образц`, `витрин`,
`маркетинг`. Остальные считаем торговыми.

Поле `quantity` верхнего уровня API суммирует **все** склады, включая
служебные. Поэтому доступный остаток **пересчитываем сами** по
отфильтрованному `stores[]`, а `quantity` из API игнорируем.

Точный список торговых складов стоит уточнить у партнёра, если он будет
на площадке. До тех пор работает фильтр выше, и это честно проговаривается
в README.

### 12.2 Описание противоречит характеристикам

Реальный пример, товар id 515291: в `name` указано «160А», в
`description` — «Номинальный ток: 160А», а в
`properties.NOMINALNYY_TOK` — «250 А».

Правило: **источник чисел — только `properties`**, то есть наше поле
`specs`, плюс `price` и пересчитанный остаток. `description` показывается
как связный текст и никогда не служит источником характеристик.

В системном промпте это должно быть сказано явно: числа берутся из полей
инструмента, модель их не пересказывает из описания и не пересчитывает.

### 12.3 Названия и артикулы грязные

`name` встречается с префиксом `***` и с продублированным артикулом в
начале. `article` бывает служебным (`200300285_`), а настоящий артикул
поставщика лежит в `properties.ARTIKULPOSTAVSHCHIKA` (`027228`).

Чистим на этапе выгрузки, в `scripts/seed-from-api.ts`, а не в рантайме
и не в промпте. Оригинал сохраняем в поле `rawName` на случай вопроса.

## 13. Грабли, на которые уже наступили

Не теоретические. Каждая стоила времени сегодня. Общее у них одно:
код выглядит рабочим, а тесты зелёные — пока не посмотришь в вывод.

**`\b` в регулярках не работает с кириллицей.** В JavaScript `\b`
опирается на `\w`, то есть на латиницу. `/\bда\b/` по русскому тексту
ведёт себя не так, как выглядит. Матчер согласия из раздела 6 поэтому
разбирает текст на слова, а не матчит границы. Не переписывать обратно.

**Регулярка, собранная из шаблонной строки, теряет escape-последовательности.**
Внутри `` `(\d{1,3})` `` последовательность `\d` превращается в букву «d»,
и выражение молча перестаёт совпадать. Только литералы: `/(\d{1,3})/`.

**Импорты в ESM поднимаются выше тела модуля.** `process.env.DB_URL = ...`
в первой строке скрипта выполнится ПОСЛЕ того, как импортированный модуль
прочитает конфиг. Смоук из-за этого молча работал на рабочей базе вместо
тестовой. Если скрипту нужно выставить окружение — подгружай модули
динамически внутри `main()`.

**`id INTEGER PRIMARY KEY` при отсутствующем `id`.** В выгрузке каталога
поля `id` не было, все 300 товаров получили ключ 0 и затёрли друг друга
через `INSERT OR REPLACE`. В базе остался один товар, а тесты проходили
на нём. Ключ теперь `sku`. Первичный ключ ставить только на то поле,
наличие которого гарантировано.

**Число из реплики нельзя брать первым попавшимся.** «Добавь R9F12110,
2 штуки» — первое число в строке это девятка ИЗ АРТИКУЛА. Количество
должно стоять отдельным словом, а не внутри буквенно-цифрового токена.

**`npm run build` при работающем `npm run dev`.** Прод-сборка перетирает
`.next` под дев-сервером, и тот начинает сыпать `Cannot find module`.
Лечится: остановить dev, `rm -rf .next`, запустить заново.

**`node -e` с кириллицей на этой машине калечит текст.** Проверки,
в которых есть русские строки, запускать файлом через `tsx`, иначе
тест соврёт — я на этом уже один раз поверил в несуществующий баг.
