# ИИ-ассистент для чата ekt.kz

Прототип для HackAlem AI, трек «Торговля». Партнёрский кейс ТОО «Электрокомплект».

Агент-консультант в одном окне чата: отвечает по каталогу электротехники —
наличие, технические характеристики, сертификаты, аналоги, условия покупки —
и добавляет позиции в корзину **только после явного подтверждения клиента**.

---

## Запуск

```bash
npm install
npm run dev
```

Открыть http://localhost:3000. Ключ к модели не обязателен: без него
приложение работает в записанном режиме и проходит весь сценарий.

С живой моделью — создать `.env.local`:

```
LLM_MODE=auto
OPENAI_API_KEY=<ключ>
LLM_MODEL=gpt-4.1-mini
```

### Проверки

```bash
npm run smoke
```

Пять приёмочных тестов кейса, через инструменты напрямую, без модели.
37 проверок, включая отрицательные: подтверждение в том же ходу,
подтверждение без согласия, повторное использование предложения.

```bash
npm run demo
```

Тот же сценарий, но через агентный цикл — видно, какие инструменты
модель зовёт и в каком порядке. С `-- --live` гоняет живую модель.

## Архитектура

Один репозиторий, Next.js (App Router) + TypeScript. Агентный цикл —
серверный route handler, каталог — SQLite. Ключ к модели живёт только
на сервере и в браузер не попадает.

```
Браузер ──POST /api/chat──▶ агентный цикл ──▶ модель (tool-calling)
   ▲                             │
   │                             ▼
   └──── SSE: токены,      8 инструментов ──▶ SQLite
         вызовы, корзина
```

| Слой | Файл | Роль |
|---|---|---|
| Конфигурация | `src/lib/config.ts` | модель, ключ, таймауты, лимиты — одно место |
| Доступ к модели | `src/lib/llm/client.ts` | стриминг, таймауты, ретраи, запасная модель, откат в mock |
| Записанный режим | `src/lib/llm/mock.ts` | весь сценарий без сети |
| Агентный цикл | `src/lib/agent/loop.ts` | модель → инструменты → результаты → модель |
| Инструменты | `src/lib/agent/tools.ts` | восемь тонких обёрток над БД + проверка согласия |
| Системный промпт | `src/lib/agent/prompts.ts` | правила поведения агента |
| Данные | `src/lib/db.ts` | схема, засев, поиск, аналоги, корзина, предложения |
| Выгрузка каталога | `scripts/seed-from-api.ts` | однократный забор данных из API партнёра |

### Инструменты

| Инструмент | Назначение |
|---|---|
| `search_catalog` | поиск по каталогу, до 5 позиций |
| `get_product` | карточка: характеристики, сертификат, цена, остатки по складам |
| `find_alternatives` | аналоги, у каждого — поле `reason` с обоснованием |
| `get_terms` | оплата, доставка, минимальная партия, самовывоз |
| `propose_add` | предложение добавить товар; **корзину не меняет** |
| `confirm_add` | добавление по подтверждённому предложению |
| `get_cart` | содержимое корзины |
| `get_cart_link` | прямая ссылка на корзину |

### Устойчивость

- **Нет сети или ключа** — `LLM_MODE=auto` уводит в записанный режим,
  сценарий доходит до конца. В шапке загорается `MOCK`: выдавать
  записанный ответ за живую модель нельзя.
- **Rate limit, 5xx, таймаут** — три попытки с экспоненциальной паузой,
  затем запасная модель, затем mock. Повтор запрещён, если часть ответа
  уже ушла пользователю.
- **Мусор в аргументах** — схема отклоняет, текст ошибки уходит модели,
  даётся одна попытка переписать вызов.
- **Смена схемы БД** — версия схемы в `PRAGMA user_version`; при
  расхождении база пересобирается сама.

## Правило подтверждения

Ключевое требование кейса: состав корзины не меняется без явного
согласия клиента. Это не строчка в промпте, а инвариант на сервере.

1. Агент никогда не вызывает `confirm_add` сам. Он вызывает `propose_add`
   и получает `proposalId`. Корзина при этом не трогается.
2. Подтверждение приходит одним из двух путей, и **решение принимает
   сервер, а не модель**:
   - **кнопка «Да»** — `POST /api/confirm` идёт из интерфейса напрямую,
     минуя модель; подделать этот вызов модель не может, потому что
     в нём не участвует;
   - **текст** — модель вправе вызвать `confirm_add`, но сервер исполнит
     его, только если сырая последняя реплика клиента проходит проверку
     на согласие. Текст реплики сервер сохраняет сам, до обращения
     к модели.
3. Предложение обязано быть создано в **предыдущем** ходу. Иначе модель
   могла бы в одном ответе вызвать `propose_add` и сразу `confirm_add`,
   подставив под проверку ту же самую фразу клиента.
4. Матчер согласия консервативный: вопросы («а можно добавить?»),
   условные конструкции («если есть на складе, добавь») и отрицания
   согласием не считаются. Сомнительное трактуется как отказ.
5. Одно предложение срабатывает один раз. Одноразовость обеспечена
   условным `UPDATE ... WHERE status='pending'` — гонкой двух запросов
   её не обойти.
6. Количество не может превысить доступный остаток. Если запрошено
   больше — добавляется доступное, и агент обязан об этом сказать.

Всё перечисленное покрыто `npm run smoke`, включая отрицательные случаи.

## Данные

Каталог — **боевая выгрузка из API партнёра**, не выдумка:

```
GET https://ekt.kz/api/products?page=N       список
GET https://ekt.kz/api/products/detail?id=N  карточка с характеристиками и складами
```

`scripts/seed-from-api.ts` ходит туда один раз и пишет `data/catalog.json`,
который лежит в репозитории. В рантайме сеть к ekt.kz не нужна: приложение
читает SQLite. Демонстрация не зависит ни от чужого API, ни от Wi-Fi.

Срез: 300 позиций. Характеристики берутся из `properties` карточки
(номинальный ток, число полюсов, напряжение, отключающая способность),
аналоги — из `properties.RECOMMEND`, то есть из собственных рекомендаций
партнёра.

### Что пришлось учесть в реальных данных

**Не все склады торговые.** В `stores[]` вперемешку городские склады и
служебные: «Брак MEGALIGHT», «Востановленный продукт», «перемещение»,
«Образцы Отдел Закупа», «Витрина ТЗ». Их остаток не считается доступным —
показать брак как наличие значит соврать клиенту. Поле `quantity` верхнего
уровня суммирует все склады, включая служебные, поэтому доступный остаток
пересчитывается по отфильтрованному списку.

**Описание противоречит характеристикам.** У товара id 515291 в названии
и описании «160А», а в `properties.NOMINALNYY_TOK` — «250 А». Источником
чисел объявлены только `properties`; описание показывается как текст и
никогда не служит источником характеристик. Это же зафиксировано
в системном промпте.

**Грязные имена и артикулы.** Названия встречаются с префиксом `***`
и продублированным артикулом; поле `article` бывает служебным
(`200300285_`), а настоящий артикул поставщика лежит в
`properties.ARTIKULPOSTAVSHCHIKA`. Чистка делается на этапе выгрузки,
оригинал сохраняется в `rawName`.

### Что синтетическое

Честно и в одном месте:

- **Сертификаты.** В API их нет, а требование кейса есть. Проставлены
  примерно трети позиций, детерминированно по артикулу, с флагом
  `demo: true`. Интерфейс и агент помечают такой сертификат как
  демонстрационный. Выдавать придуманный сертификат за настоящий нельзя.
- **Условия покупки** (`data/terms.json`) — оплата, доставка, минимальная
  партия, самовывоз. Этих данных в API тоже нет. ТЗ разрешает синтетику
  с сохранением структуры полей.

Всё остальное — артикулы, названия, цены, характеристики, остатки,
рекомендации — реальные данные партнёра.

## Ограничения, заложенные намеренно

Из требований кейса:

- агент **не оформляет заказ** — последний шаг это ссылка на корзину;
- **не запрашивает и не хранит платёжные данные**;
- **не меняет корзину** без явного подтверждения;
- **не сообщает недостоверных данных** о цене и наличии: все числа
  приходят из инструментов, модель их не придумывает и не пересчитывает;
- если данных нет — говорит, что не нашёл, и предлагает связаться
  с менеджером. Выдумывать артикулы запрещено.
